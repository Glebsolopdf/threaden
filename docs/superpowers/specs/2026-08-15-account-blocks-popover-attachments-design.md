# Исправление account-блокировок, меню сообщений и вложений

## Цель

Исправить три независимых бага без изменения несвязанных сценариев:

1. временная блокировка аккаунта не должна распространяться на другие аккаунты;
2. меню действий сообщения должно быть устойчивым overlay, привязанным к выбранному сообщению;
3. сообщение с вложением должно отправляться без текстовой подписи.

## Диагностированные причины

### Блокировка

Текущий `/blocked` показывается клиентом при любом HTTP 429. Backend проверяет активную временную блокировку в общем middleware по ключу `ip:<client IP>`. Поэтому аккаунты, использующие один IP, разделяют состояние.

### Меню действий

Компонент меню находится внутри сообщения и устанавливает `position: fixed`, но вычисляет координаты из точки pointer/contextmenu. Координаты не привязаны к прямоугольнику сообщения и не пересчитываются при прокрутке, изменении окна или размера сообщения.

### Вложения

Multipart-путь уже передаёт пустое тело в `SendWithAttachments`, но обычный `Send` отвергает пустое тело без учёта наличия вложений. На клиенте текущий composer уже использует условие `files.length > 0 || trimmedBody.length > 0`; этот контракт должен быть закреплён backend-тестами и проверен во всех рендерах сообщений.

## Архитектура решения

### Account-scoped блокировки

Сохранить IP-блокировку для анонимных запросов и атак, которые нельзя связать с аккаунтом. Для авторизованного запроса после аутентификации проверять отдельное состояние блокировки по `user ID`; account key не должен включать IP.

Установка account-блокировки должна записывать user ID и время истечения. Проверка должна:

- выбирать только запись указанного user ID;
- удалять или игнорировать истёкшую запись;
- возвращать отдельный код ошибки для account block;
- не влиять на другой user ID;
- сохранить существующий IP-ban flow для анонимных запросов.

Тесты покроют установку, снятие/истечение и параллельную работу аккаунтов A/B.

### Overlay меню

Меню будет монтироваться в document-level overlay, чтобы не менять высоту и положение сообщения. Якорем остаётся DOM-элемент сообщения/пузыря, а не координата pointer.

Позиционирование:

1. получить `getBoundingClientRect()` anchor;
2. измерить меню после mount;
3. предпочесть размещение непосредственно над anchor;
4. если сверху недостаточно места, разместить снизу;
5. ограничить left/top viewport с безопасным отступом;
6. пересчитывать на scroll, resize и через `ResizeObserver` для anchor/menu;
7. закрывать observers/listeners при unmount и закрытии.

Мобильный long-press будет использовать тот же anchor-based расчёт. Существующую swipe-to-reply механику не менять.

### Сообщения с вложениями

Доменное правило:

```text
trimmed body is non-empty OR attachment count > 0
```

Оно применяется в multipart API и в сервисе сообщений. Пустое тело без вложений остаётся запрещённым. История, reply preview, уведомления и список сообщений должны отображать attachment-only сообщение без обращения к обязательному тексту.

## План тестирования

- backend unit/integration: account block isolation and expiry;
- backend integration/API: text-only, text-plus-attachment and attachment-only submission;
- frontend unit/component: composer send eligibility and attachment-only rendering;
- frontend component: overlay position is derived from anchor and clamps/falls back above/below;
- existing Go, Angular, build, lint/type checks and source-limit script.

## Ограничения и совместимость

Не менять публичный формат обычного сообщения. Для account block добавить только необходимый error code/transport behavior. Не добавлять новую библиотеку, если существующий Angular stack позволяет реализовать overlay через текущие платформенные API или уже установленную зависимость. Не затрагивать unrelated attachment quota changes в рабочем дереве.
