# Голосовые сообщения

## Цель

Добавить в групповые сообщения два способа отправки аудио: запись с микрофона
непосредственно в браузере и прикрепление готового аудиофайла. Аудио должно
оставаться обычным вложением, чтобы использовать уже существующие квоты,
хранение, события удаления и автоматический TTL.

## Границы и согласованные правила

- Запись с микрофона ограничена пятью минутами и останавливается автоматически
  по достижении лимита.
- Готовые аудиофайлы проходят через существующий multipart endpoint сообщений.
- Аудио считается одним вложением; действующий максимум — три вложения на
  сообщение.
- Аудио входит в активную квоту пользователя, суточный лимит нового аккаунта,
  общую квоту хранилища и проверку свободного места.
- Аудио хранится столько же, сколько остальные вложения, и удаляется cleanup
  сервисом по `ExpiresAt` (текущий срок — 72 часа).
- Поддерживаются WebM/Opus, OGG/Opus, MP3, WAV и M4A/MP4. Формат проверяется
  по содержимому и MIME, а расширение используется только как вспомогательный
  сигнал.
- Аудио не перекодируется: после проверки оно сохраняется как бинарное
  вложение.

## Архитектура

### Backend

Существующий домен `attachments` получает новый `KindAudio`. Детектор формата
распознаёт согласованные аудиоформаты, а процессор копирует проверенное аудио в
временный файл с тем же жизненным циклом, что и обычный файл. `storage.Service`
создаёт метаданные с `KindAudio`, резервирует размер через текущие методы quota
и назначает тот же retention.

Multipart API и групповой сервис не получают отдельный endpoint: голосовое
сообщение отправляется как `files[]` через существующий маршрут. Публичная
модель вложения расширяется значением `audio`; cleanup, удаление сообщения,
удаление аккаунта и realtime-события продолжают работать без специальных
веток.

### Web-клиент

Композер сообщения получает отдельное управление записью. Состояния записи:
ожидание, запись, готово к отправке и ошибка. Используется браузерный
`MediaRecorder`; предпочтительный формат выбирается через
`MediaRecorder.isTypeSupported`, с fallback на доступный аудиоформат. Таймер
ограничивает запись пятью минутами. Пользователь может остановить или отменить
запись, после чего результат отправляется как одно обычное вложение.

Существующий выбор файлов принимает аудио вместе с другими вложениями. Для
аудио-предпросмотра используется HTML `audio controls`; остальные типы остаются
без изменений. Если MediaRecorder или доступ к микрофону недоступен, клиент
показывает ошибку и не блокирует загрузку готовых файлов.

## Поток данных

1. Пользователь выбирает готовый аудиофайл или завершает запись.
2. Клиент валидирует количество и размер, формирует `FormData` с `files[]`.
3. Backend определяет тип по содержимому, проверяет размер и передаёт аудио в
   общий `storage.Service`.
4. Сервис резервирует место в тех же квотах, сохраняет файл и создаёт запись
   вложения с `ExpiresAt = CreatedAt + Retention`.
5. Сообщение возвращается через HTTP и realtime с вложением `kind: audio`.
6. По истечении TTL cleanup удаляет бинарный файл и запись метаданных так же,
   как для существующих вложений.

## Ошибки и безопасность

- Пустые, слишком большие, повреждённые или неподдерживаемые аудиофайлы
  отклоняются существующими кодами ошибок вложений.
- Размер входного аудио ограничивается текущим `MaxInputMediaBytes`; отдельный
  параллельный лимит и отдельная квота не вводятся.
- Клиент освобождает `Blob`-ресурсы и отменяет активную запись при отмене,
  отправке или уничтожении компонента.
- Сервер не доверяет расширению и не публикует внутренний путь хранения.

## Тестирование

Backend-тесты покрывают распознавание каждого согласованного формата, отказ
неподдерживаемого формата, обработку `audio` в процессоре и сохранение
метаданных с общим TTL. Существующие тесты quota и cleanup должны подтвердить,
что аудио участвует в суммах и удаляется тем же проходом.

Web-тесты покрывают классификацию и валидацию аудио, отображение аудиовложения,
отправку multipart и переходы записи: старт, остановка, автостоп через пять
минут, отмена и ошибка доступа к микрофону.

## Планируемые границы файлов

- `backend/internal/attachments/limits.go` — новый вид `audio`, менее 120 строк.
- `backend/internal/attachments/detect.go` и `processor.go` — аудиодетекция и
  passthrough без превышения 220 строк на файл.
- `backend/internal/attachments/audio/` — отдельный модуль проверки сигнатур,
  если он потребуется после тестов; не более пяти исходных файлов в каталоге.
- `web-client/src/app/features/groups/attachments/` — существующие компоненты
  только для подключения поведения; запись и её состояние — в отдельной
  поддиректории `voice/`.
- Тесты размещаются рядом с изменяемыми backend-модулями и в существующей
  структуре web-тестов.

Новые зависимости не требуются.
